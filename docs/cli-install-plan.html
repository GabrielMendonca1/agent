Installable Agent CLI from Releases

Why · 1 request quero uma cli instalavel que nem o claude code

A user with Node and GitHub CLI installs Agent without a build.

What does the user download?
Then install.sh only wraps the commands in docs/setup.md. Each install clones Pi, runs npm ci, check, build and the patch tests.
The updater, wrapper and launcher are Node scripts, and extensions load through jiti. A Bun binary changes the runtime that the gate tested.

install.sh downloads the tarball only if Node is 22.19 or newer.

Who can download the release?
Then install.sh also accepts curl. The URL https://github.com/GabrielMendonca1/agent/releases/latest/download/install.sh works only after the repo is public and a release exists.
 The installer must reject unsafe archive paths and links before extraction. It must use an HTTPS release from the selected repository. SHA256SUMS detects damaged files; it does not prove the publisher identity by itself.

The bundled updater activates the tarball with no build.

agent-update.mjs:2150 · promote()

A download cannot match it, so the new mode skips the receipt.

The installer registers resources in ~/.agent, not in ~/.pi/agent.

The updater must default to ~/.agent and keep explicit profile overrides.

The user types agent and logs in with their own account.

The wrapper fixes the profile to ~/.agent for every command.

Settings, auth and sessions stay in ~/.agent. Model login does not enable web search. First-use help must name the optional Google or OpenRouter credentials. Missing search credentials must not block chat.

A new terminal finds agent through the PATH block.

fish and other shells get no block.

agent update installs the latest release; rollback restores the last one.

The wrapper sends agent update to the release download, not to a rebuild.

The maintainer builds one tarball from the checkout and publishes it.

agent-dist reuses --prepare and packs the release with the bundle.

The release metadata records the commit but not the local checkout path.

One gate check proves install, update and rollback in a temporary HOME.

A manual clean-machine run uses a real tarball before each publish.

Shared: the tarball layout and its artifact.json.

Not changing: Pi base, patches, build pipeline, Windows, runtime opt-in.

  • Pi 1.5.0 base, the 10 patches in overlay/ and the gate in agent-update.mjs stay as they are.
  • No npm package. The updater installs a tested tree with rollback; npm install -g skips that.
  • Windows keeps the checkout path in docs/setup.md. Windows is not validated on a real machine. A later Windows installer needs its own artifact validation.
  • The runtime opt-in (--agent-enable --juice-home) stays manual.
  • The Mark store ~/.local/share/pi-overlay and ~/.pi/agent are not touched.
  • No CI workflow. The maintainer runs agent-dist.mjs and publishes after approval.
  • Files: new scripts/install.sh, scripts/agent-dist.mjs, scripts/test-install-artifact.mjs; changed agent-update.mjs, agent-wrapper.sh, .pi/checks.json, docs/setup.md, README.md. The new release check must fail if candidate startup does not run.
